## 缺陷

### D-01（低，对应 G-13、G-20）三个写用例用事务外读到的行快照算 `changes`，并发改同一目标时事件的 from 值可能失真

- **位置**：`modules/identity/admin-accounts.ts` 的 `updateAccount`（第 151 行 `findById` 在事务外，第 159–163 行用这份快照算 `changes`，行锁只用来数数、不回读最新值）；`setAccountDisabled`、`deleteAccount` 同款（账号都在事务外读）。
- **场景**：真 Postgres 上两个管理员并发操作同一个目标（甲读快照后、开事务锁行前，乙已把目标降级并提交），甲的事务里 `lockEnabledAdmins` 数出来的是新值、护栏判得对，但写下去的事件 `changes.isAdmin = { from: true, to: false }` 里那个 `from` 已经不是库里的真值；同型还有「把已不是管理员的行当减员去锁、去算」。
- **为什么现在才发现不了**：进程内的库一次只跑一个事务，串行下快照永远新鲜；规格 G-20 的并发场景本来就标注只在真 Postgres 上验（规格「未确定」）。护栏本身（数出来的那个数）是对的——锁下的计数准确，**失真的只是事件留痕里的前后值**，属于审计精度问题，不是权限口子。
- **期望**：事务内锁完行后把目标行重读一遍再算 `changes`（`lockEnabledAdmins` 的返回值本来就带着最新行，弃之只用计数可惜），或模块卡里把这条已知边界记下来。
- **复现（读码）**：`admin-accounts.ts` 151 行（事务外 findById）→ 168–170 行（用快照算 `demotesEnabledAdmin` 和 `changes`）→ 171–174 行（事务内只数数不回读）。

### D-02（低，整洁度，对应规格事件表）设计文档的事件一节没跟上契约包的四段放宽

- **位置**：`docs/changes/2026-11-26-dev-face/design-03-people.md` 第 136 行仍写「事件名过契约包的 `eventName`（三段的名字第 1 片已经放行）」；实现已放宽到四段（`packages/contracts/src/events.ts` 的正则 `{0,1}`→`{0,2}`，注释带日期），放宽这件事在契约文件的注释和 `modules/identity/module.md` 的事件表（列着 `identity.user.password.reset`）里有记，设计文档这一句没更新。
- **期望**：设计文档跟着改成「四段的名字这一片放行」，或加一行指向契约包的注释。文档内部的快照口径以实现为准（架构文档纪律），这里只是补一句的事。

## 两处申报偏离的核查

**(a) 契约包 `eventName` 放宽到四段。** 结论：必要、正确、已记录，放宽是收口的不是敞口的。规格的人员事件表本身就定了 `identity.user.password.reset` 这个四段名（G-36 的表），第 1 片放行的正则最多三段，不放宽这个名字过不了契约。实现把 `(?:\.[a-z][a-z-]*){0,1}` 改成 `{0,2}`，注释带日期与来由（2026-11-28）；单元测试「四段的名字也合法（人员规格的 identity.user.password.reset，2026-11-28 放宽）；两段的照旧合法」同时断言五段、空段、大写段仍然被拒——放宽恰好到规格要的那一级。**活进程实弹：这个四段事件真的发出来了**（停服对账 `identity.user.password.reset` 1 条，payload 键 `userId/actorId/revokedSessions`）。唯一挂账：设计文档 03 还写着「三段」（D-02）。

**(b) 两个 409 都命中时 `identity_last_admin` 优先于 `identity_self_change`。** 结论：自洽，而且严格说这不是偏离规格，是把规格自己的话落实。G-18 的验收写「只剩一个启用的管理员时：降级、停用、删除各回 409 `identity_last_admin`」——而那个唯一的管理员必然就是操作者本人（走得到 admin 路由的只有管理员，停用的登录不了），所以这一句已经替两道闸定了先后；反过来如果 `self_change` 先说，G-18 的验收就打不出来。实弹矩阵（活进程）：唯一管理员对自己**降级/停用/删除** → `identity_last_admin`；唯一管理员**给自己重置口令** → `identity_self_change`（重置不减管理员数，数量那道闸本来就不该拦，G-19 照说）；两个管理员时对自己的四个动作全 → `identity_self_change`，对别人 → 200。单元测试「最后一个管理员停用自己：两个 409 都命中，数量那道闸先说」把这条钉死。**记录齐**：代码注释（admin-accounts.ts 与 admin-guard.ts，带日期）、模块卡「规格没写到、实现时定下的」第三条（把为什么说全了：数量那道更具体、也让五个失败码在集成里打得到）、集成测试文件内的注释三处一致。
