## 它管什么

管四条路由（登录、退出、我是谁、改密）和它们底下的东西：口令散列、会话的生成与吊销、登录锁定、写请求的跨站防护、审计事件，外加一个建账号的命令行脚本。健康探测不在这一片做，只写它与登录的关系。

不管：用户组与工程授权、建号改号的界面和路由（第 3 片）、单点登录和跨实例的票、健康探测本身（系统模块已有）。旧系统的哪些做法属于这家单位的策略而不是通用机制，见「明确不做的」。

## 术语

| 词 | 意思 |
|---|---|
| 账号 | 一行记录：用户名、口令散列、管理员位、停用位 |
| 令牌 | 一串密码学随机数，放在会话 cookie 里 |
| 会话 | 库里的一行：令牌的散列、所属账号、过期时间 |
| 来源地址 | 请求头 `X-Real-IP` 的值；没有这个头时取连接的对端地址。只写进事件，不参与锁定 |
| 请求的协议 | `X-Forwarded-Proto` 的最后一跳；没有这个头时是 `http` |
| 写方法 | `GET`、`HEAD`、`OPTIONS` 以外的方法 |
| 对外地址 | 配置项 `PUBLIC_ORIGIN`；没配时是请求自己的地址（I-37） |
| 锁定的键 | 用户名，比较时不分大小写 |
| 窗口 | 900 秒。失败只在窗口内计数 |

来源地址和请求的协议这两个头，都假定是反向代理改写后转进来的（新仓还没有部署配置，见「未确定」）。
下文的「任务书」是 `docs/charter.md`；R 编号在 `docs/parity/routes.csv`；B 编号在 `docs/parity/backlog.md`；测试文件名在旧仓 `server/tests/`。

## 要求

每条三样：一句要求、来源、怎么验。验收只用四种测试：单元测试不碰数据库；集成测试用进程内数据库打真路由，凡要读库的断言都放这里；契约测试读生成的接口文档；端到端起真浏览器。涉及时间的验收（I-13、I-14、I-22、I-23）用模块注入的时钟拨表，不真等。

### 路由与总则

| 路由 | 访问级别 | 请求体 | 成功时 |
|---|---|---|---|
| `POST /api/v1/auth/login` | public | `{ "username": 1 到 64 个字符, "password": 1 到 128 个字符 }` | 200 `{ "user": User }`，带会话 cookie |
| `POST /api/v1/auth/logout` | user | 无 | 200 `{ "ok": true }`，带清除 cookie |
| `GET /api/v1/auth/me` | user | 无 | 200 `{ "user": User }` |
| `POST /api/v1/auth/password` | user | `{ "currentPassword": 1 到 128 个字符, "newPassword": 1 到 128 个字符 }` | 200 `{ "ok": true }`，带新的会话 cookie |

`User` 一律是 `{ "id": 字符串, "username": 字符串, "displayName": 字符串, "isAdmin": 布尔 }`。登录直接把人带回来，页面不用再问一次「我是谁」。`id` 是别的模块记录「这件事是谁做的」时用的编号：用户名是给人看的，编号才是不变的。

| 错误码 | 状态码 | 什么时候 |
|---|---|---|
| `auth_required` | 401 | 没登录、会话失效或已被吊销 |
| `auth_invalid_credentials` | 401 | 登录时用户名或口令不对，两种情形同一个回应 |
| `auth_locked_out` | 429 | 用户名处于锁定；`details.retryAfterSeconds` 是还要等的秒数 |
| `auth_forbidden` | 403 | 已登录但级别不够 |
| `auth_account_disabled` | 403 | 登录时口令正确，但账号已停用 |
| `csrf_origin_mismatch` | 403 | 写请求的 `Origin` 与对外地址不一致，或者是 `null` |
| `auth_current_password_wrong` | 400 | 改密时旧口令不对 |
| `auth_password_too_weak` | 400 | 新口令短于最短长度 |
| `auth_password_reused` | 400 | 新口令与旧口令相同 |

`message` 是给人看的，文案不固定；只有 I-10 要求两种情形逐字相同。请求体不合一律是已有的 `invalid_request`（400）。

### 口令散列

| 编号 | 要求 | 来源 | 验收 |
|---|---|---|---|

### 登录与锁定

| 编号 | 要求 | 来源 | 验收 |
|---|---|---|---|
| I-09 检查顺序 | 当处理登录请求时，系统应依次查形状、锁定、口令、停用，都过了才成功。停用查在口令之后。 | R059（pages.py:80-115）；`test_devonly_retire.py` 钉住「资格闸在验密之后」 | 集成测试——停用账号用错口令得 401 `auth_invalid_credentials`，用对口令得 403 `auth_account_disabled` |
| I-10 用户名或口令不对 | 当用户名不存在、账号没有口令、或口令不对时，系统应回 401 `auth_invalid_credentials`，三种情形的状态码、错误码、message 完全相同。 | R059（pages.py:112）；占位账号和无口令的行各有专属文案（pages.py:86-99）是存在性枚举口 | 集成测试——三种情形的响应体去掉 `requestId` 后逐字相等 |
| I-11 抹平时序 | 当登录请求形状合法且未被锁定时，系统应恰好做一次 argon2id 校验，不论用户名存在不存在、账号有没有口令、口令对不对；用户名不存在或账号没有口令时，对一份固定的假散列做。 | R059（pages.py:100-106）；`test_login_oracles.py` | 单元测试——把散列函数换成计数桩，四种情形的调用次数都是 1 |
| I-12 记失败 | 当用户名或口令不对时，系统应给「提交的用户名，不分大小写」这一把键记一次失败。用户名不存在也同样记。每次记的时候顺手删掉全表窗口外的记录。 | R059（pages.py:107-112；auth.py:27-28、294-316）。新版不按来源地址另记一把：来源地址靠代理头带进来，可以伪造，按它计数挡不住分散的尝试 | 单元测试——失败一次后这把键的计数加一；把用户名换一个大小写再错，同一把键继续加；窗口外的旧记录消失 |
| I-13 锁定 | 当某个用户名在窗口内的失败数达到 5 次时，系统应拒绝这个用户名后续的登录 900 秒，从第 5 次失败那一刻算起。 | R059（auth.py:27、319-337）是按来源地址 5 次、按用户名 15 次；`test_boundaries.py`、`test_security_hardening.py`。锁定时长不从窗口里最早一次失败算起：旧系统那样做，最短只锁 1 秒（auth.py:336） | 单元测试（注入时钟）——连错 4 次都是 401，第 5 次失败后进入锁定；第 6 次 429；从第 5 次起满 900 秒后再错，回 401，并按新的窗口重新计数 |
| I-14 锁定的回应 | 当用户名处于锁定时，系统应回 429 `auth_locked_out`，`details.retryAfterSeconds` 是还要等的秒数，向下取整，最小 1。锁定期间不验口令，正确口令也进不来，不再记失败。 | R059（pages.py:80-84）；台账 BUG-2026-11-15-163（秒数只在文案里，被客户端吞掉） | 集成测试——429 的 `retryAfterSeconds` 在 1 到 900 之间；换成正确口令仍 429；失败记录不再变 |
| I-15 锁定存在库里 | 当进程重启后，系统应保持重启前的失败记录和锁定。 | 新决定；R059 的计数在进程内存里，重启即清（auth.py:26） | 集成测试——同一数据库上错 4 次，重建模块和应用后再错 1 次，第 6 次 429 |
| I-16 成功清计数 | 当某个用户名登录成功时，系统应删掉它的失败记录。 | R059（pages.py:128-129） | 单元测试——错 4 次后登录成功，再错 4 次都不锁 |
| I-17 锁定不波及 | 当某个用户名被锁定时，系统应照常受理别的用户名登录，健康探测也应照常回 200。 | R057、R059 | 集成测试——锁住一个用户名后，另一个账号登录得 200 |

### 会话与 cookie

| 编号 | 要求 | 来源 | 验收 |
|---|---|---|---|
| I-18 令牌 | 当登录成功时，系统应生成至少 32 字节的随机令牌放进 cookie，库里只存它的 SHA-256 散列。 | 新决定（编排者） | 集成测试——登录后读会话表：没有一行含令牌原文，有一行的散列等于 cookie 值的 SHA-256 |
| I-19 cookie 属性 | 当种会话 cookie 时，系统应写 `nexus_session=<令牌>`，带 `Path=/`、`HttpOnly`、`SameSite=Lax`、`Max-Age=2592000`，不写 `Domain`。 | R059（pages.py:146-147）；`test_cookie_scope.py` 只钉了 `Path` | 集成测试——解析 `Set-Cookie` 逐项断言 |
| I-20 Secure | 当请求的协议是 `https` 时，系统应给会话 cookie 加 `Secure`；否则不加。进程自己不终结 TLS，协议只认请求头。 | R059（pages.py:24-30、146-147）；台账 BUG-2026-10-29-62；`test_dev_login_cookie_secure_on_https`、`test_dev_login_cookie_plain_on_http` | 集成测试——带 `X-Forwarded-Proto: https` 时有 `Secure`，不带时没有 |
| I-21 令牌不进正文 | 任何响应正文都不应出现令牌；这一片不认 `Authorization` 头。 | R059 把令牌回给本机端（pages.py:148-150）；本机端不进新版（任务书 D-2） | 契约测试——四条路由的响应里没有 `token` 字段。集成测试——登录、我是谁、改密的正文都不含 cookie 值；带 `Authorization: Bearer <令牌>`、不带 cookie 调我是谁得 401 |
| I-22 有效期与顺延 | 当带着有效会话的请求进来、而这条会话的剩余有效期已经不足 15 天时，系统应把过期时间改成「此刻加 30 天」，并在响应里重发同一个 cookie（`Max-Age` 不变）。剩余还多的时候不动库、不重发。没有绝对上限。 | 编排者；旧票自签发起 30 天绝对过期，不顺延（auth.py:57、75）。不做成每个请求都续：那等于给每个读请求加一次写 | 集成测试（注入时钟）——登录后第 14 天用一次，响应不带 `Set-Cookie`，库里的过期时间不变；第 16 天用一次，带 `Set-Cookie`，过期时间变成第 46 天；第 40 天用一次仍得 200。一直没用，满 30 天回 401 |
| I-23 会话无效 | 当 cookie 里的令牌在库里找不到，或已满有效期时，系统应回 401 `auth_required`。过了有效期的会话行在下次登录时删掉。 | R059、R060 | 集成测试——伪造的令牌得 401；过期行在登录后消失 |
| I-24 退出 | 当已登录用户调退出接口时，系统应删掉会话行，回 200 `{ "ok": true }`，并发一个清除 cookie 的 `Set-Cookie`（同名、`Path=/`、`Max-Age=0`、过去的 `Expires`）。被复制走的旧 cookie 随即失效。 | R060（pages.py:153-157 只清 cookie，票不吊销） | 集成测试——复制 cookie 后退出，拿复制件调我是谁得 401 |
| I-25 没登录就退出 | 当没有有效会话的人调退出接口时，系统应回 401 `auth_required`。 | 编排者定的级别 user | 集成测试 |

| I-38 配置合法 | 当给了 `PUBLIC_ORIGIN` 时，系统应在启动时校验它是不带路径的 `http` 或 `https` 地址，不合法就启动失败。 | 新决定（`apps/api/src/config.ts` 的既有做法） | 单元测试 |

## 旧系统的做法与教训

读的是旧仓 `server/nexus_server/` 下的 `dev/routers/pages.py`、`core/auth.py`、`core/guard.py`、`identity/registry.py`，加 `server/tests/` 里的相关测试。行号是 2026-11-26 的现状。旧系统一次都没跑过，标「读码所见」的都没有实测。

- **登录口的顺序与枚举口。** R059 依次查锁定、占位账号、无口令材料、口令、停用、开发者旗、管理员旗（pages.py:80-127）。占位账号和无口令材料的行各有一句专属文案，并且不做假散列（pages.py:86-99）；抹时序只做在「用户名不存在」上（pages.py:100-106），`test_login_oracles.py` 在开发面也只测了这一种。`test_placeholder_user.py` 的 `test_login_gates_placeholder` 把「占位账号」文案钉住了。（→ I-10、I-11）
- **停用查在口令之后。** 口令对了才回 403「账号已停用」，等于替人确认口令猜对了；这一次不计失败（pages.py:107-115）。（→ I-09）
- **锁定。** 两把钥匙，阈值 5 和 15，窗口和锁定都是 900 秒（auth.py:27-28）。注释写「锁 15 分钟」（auth.py:320），实际是到窗口内最早一次失败满 900 秒为止，可以短到 1 秒（auth.py:336）；`test_boundaries.py` 的 `test_lock_countdown_bounds` 钉的就是这个。计数在进程内存里，重启即清（auth.py:26）。开关 `login_lockout` 每次读盘，缺省开，设它是为了本机端自动重试不把计数烧满（auth.py:32-38）。登录口的锁定接线没有测试，只有 `_locked` 纯函数有。全局那把钥匙让任何人都能把一个用户名锁住，这是有意的取舍（pages.py:72-74）。（→ I-12 到 I-17）
- **票是无状态的。** `用户名.时间戳.签名`（auth.py:57-64）；签名的材料绑口令版本，所以改密能吊销旧票（`test_token_binds_pwv`）。有效期是签发起 30 天绝对过期（auth.py:21、75），没有顺延。退出只清 cookie（R060，pages.py:153-157），复制走的票照样有效。停用即时失效，但重新启用后未过期的旧票会复活（auth.py:78-80，读码所见）。开发面登录把令牌也放进响应正文（pages.py:148-150）。（→ I-18、I-21 到 I-24、I-29）
- **cookie。** `HttpOnly`、`SameSite=Lax`、`Path=/`、30 天，https 来路加 `Secure`（pages.py:24-30、146-147）。`Path=/` 是 0.53.1 的事故换来的（pages.py:143-144 的注释），`Secure` 是台账 BUG-2026-10-29-62 补的。旧测试只钉了 `Path` 和 `Secure` 两项（`test_cookie_scope.py`）。（→ I-19、I-20）
- **我是谁。** R058 没有鉴权依赖，匿名回 200 加空用户（pages.py:46-67）。它回开发者旗、管理员旗、超管旗、可见工程；超管的判据之一是「在一个固定名字的用户组里」（auth.py:227-254），页面显隐与真正的闸分叉过（pages.py:64-66 的注释）。开发面的我是谁和退出，在旧测试里找不到断言。（→ I-26、I-27）
- **改密。** R064 先查新口令长度（至少 6），再验旧口令；旧口令不对回 401 且不计锁定（pages.py:370-372）；没有「新旧相同」的检查；成功后口令版本加一并立刻换发新票（pages.py:382-386；`test_passwd_happy_reissue`）。（→ I-30 到 I-33）
- **用户名。** R135 的正则是字母、数字、下划线、连字符，报错文案却写「还有点和百分号」（identity/registry.py:328-329）；没有长度上限（同文件第 155 行）。登录请求的用户名也没有上限，口令上限 128（pages.py:37-38）。（→ I-02、I-34）
- **跨站防护。** `core/guard.py` 只管写方法。先查 `Host` 在白名单里（本机地址、网卡地址、登记表里的入口域名），再查 `X-Forwarded-Host` 的每一跳，然后三通道放行：不带 `Origin`、`Origin` 在白名单、`Origin` 与 `Host` 同主机同端口；其余 403（guard.py:141-163；`test_review.py` 的 `test_guard_write_ok`、`test_guard_write_ok_xfh`）。它非要查 `Host`，是因为旧鉴权对回环来源免登录（auth.py:120-128），不查就被域名重绑定打穿。新版没有按来源免登录这回事，所以不查 `Host`。白名单惰性重算时在请求路径上跑同步子进程（guard.py:38-42）。（→ I-35 到 I-38）
- **三处各自实现的会话。** 开发面、生产面、探测器各写了一套登录和 cookie（prod/app.py:317-376；cyberneticscore/observer.py:131-188），回应形状和 cookie 属性都不一样。修一处漏两处的账：台账 BUG-2026-10-29-43（生产面缺全局锁和开关）、BUG-2026-10-31-24（开发面 14 处留痕没接来源地址）。这一片只有一份实现。
- **B-002。** 授权画布的数据源把整张人员表回给页面，带盐和散列（R073，dev/routers/platform_routes.py:102-125）；身份模块自己的名单是剥掉的（R133，identity/registry.py:101）。全平台的响应字段扫描闸不在这一片，I-45 只管这四条路由。
- **B-003。** 超管判据靠用户组的名字（auth.py:227-254）；注释说这个组的维护端点有审计（auth.py:229-231），端点里没有审计调用（R077，platform_routes.py:219-272）。（→ I-27、I-48）
- **B-011。** 改用户组不记审计，建组和删组记（identity/registry.py:582、586-605、614）。（→ I-41）

## 明确不做的

- 单点登录和桥接票：旧系统的身份权威与换票是另一条线（任务书 §7.1），等生产面和控制芯核的提案。
- 跨实例的票：旧系统每台实例各存一份口令材料，票在本机签发；新版只有一个库，会话只在一处。
- 用户组与工程授权：第 3 片。
- 建号、停用、删号的界面和路由：第 3 片。这一片只有一个命令行脚本和一个置停用位的用例。
- 超管、开发者旗、可见工程集：是这家单位的权限模型（R058、R059 的清点结论），不进内核的我是谁。
- 只许管理员口令直登：同上，是这家单位后来收口的策略；内核里任何启用且有口令的账号都能登录。
- 找回口令：要邮件或短信通道，这一片没有。
- 给智能体和脚本用的接口令牌：这一片只有浏览器会话。
- 会话列表与逐个吊销的页面：没有提出这个需求；吊销的能力本身有（I-24、I-29、I-30）。
- 锁定开关：旧开关是为本机端的自动重试设的，本机端不进新版；测试用注入的时钟跳过窗口。
- 改用户名：用户名是事件的 `subject`，这一片不动它。
- 页面与接口不同源的部署：只支持同源（任务书 §3.4 的默认），跨域白名单另议。
- 兼容旧口令散列、保留旧路径：都不做（任务书 §7.4；编排者的约定）。

## 未确定

- 旧系统在反向代理后面怎么取来源地址：代码取的是连接对端（pages.py:77），部署有没有把真实地址转进来，没读到。
- 新仓还没有反向代理的部署配置。规格按「代理改写 `X-Real-IP` 和 `X-Forwarded-Proto`」写，部署配置落下来时要对一遍。
- 改密时旧口令不对发不发事件：本片只记失败（I-31），不发事件。要补的话名字用 `identity.password.change-failed`。
- 旧系统停用后重新启用，未过期的旧票是否真的复活：读码如此，没实测。
- 旧跨站闸对 IPv6 字面量 `Host` 怎么处理：它按第一个冒号切主机名（guard.py:143），带方括号的地址会被切成陌生主机。读码如此，没实测。
- 真实域名下的端到端（任务书 §11 条款 4）：本机只能走回环加页面代理，留到发布前。
