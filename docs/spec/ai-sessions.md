## 它管什么

管开发者在工程里和代理打交道的一整段，十七条路由和它们底下的东西：会话记录；平台在服务器上拉起、监管、收回的代理进程；平台自己写的对话轨迹；对话附件；沙盒——任务分支、工作树、记录、合入与废弃；完工回执；一个工作台总览；一组事件；一个可替换的检查点。

下文把这一片叫「会话模块」。代码里是一个模块还是几个、怎么拆文件，归设计；任务卡上的领域名是 `sessions`。

不管：任务队列的派发、自动合入、工位回收（第 5 片。这一片只把它们要用的沙盒和会话能力做成用例）；回执的收件箱页面、已读位置、分流到控制芯核之后的后果（第 8 片）；安检的模型层、配置和管理面（第 8 片。这一片只留检查点、接上规则层）；预览、发布（第 6 片及以后）；模型网关、按工程选模型。旧系统的哪些做法不带进新版，见「明确不做的」。

## 术语

| 词 | 意思 |
|---|---|
| 代理 | 替一个会话干活的进程。在服务器上，由平台拉起、监管、收回 |
| 助手 | 配置里的一个条目：平台知道怎么拉起它、怎么读它的输出。有编号、名字，还有此刻能不能用 |
| 适配器 | 平台和某一种助手之间的翻译：把助手的输出翻成平台认的事件 |
| 假助手 | 仓里自带的一个脚本，按平台认的格式说话，行为可控，给测试用 |
| 会话 | 库里的一行：一段对话，加它的代理进程的状态 |
| 主会话 | 每个工程恰有一段的那段会话，默认的对话 |
| 聊天位 | 另开的一段有名字的会话，能力同主会话 |
| 沙盒会话 | 跟着沙盒走的会话，在沙盒的工作树里干活 |
| 说会话 | 主会话和聊天位的合称 |
| 状态 | 代理进程的状态：stopped 没在跑、starting 拉起中还没就绪、running 在跑 |
| 工作态 | 代理正在处理一轮：从它报告开始，到它报告结束 |
| 轨迹 | 一个会话的对话记录，一条条条目，平台写 |
| 条目 | 轨迹的一行：序号、种类、文本等 |
| 回合 | 代理从开始处理到报告结束的一轮 |
| 沙盒 | 工程仓库的一条任务分支、它的一棵工作树、一条记录 |
| 任务名 | 沙盒或聊天位的名字 |
| 任务分支 | 沙盒专用的分支，名字是 `nexus-task/<任务名>` |
| 配额 | 一个工程同时能有的在役沙盒数、在跑的聊天位数 |
| 回执 | 代理干完活交给平台的报告：结论、状态、要人裁决的事、派生的事 |
| 受众 | 回执给谁看。user 是这个工程的人，platform 是平台自己 |
| 会话凭据 | 平台拉起代理时发给它的、只属于这个会话的一串秘密，只够交回执 |
| 附件 | 对话里带的图片或文件，临时素材 |
| 检查件 | 一个可替换的部件：看一段文字里有没有凭据，回答放行、脱敏还是拦截 |
| 调用者 | 当前登录的账号：编号、是否管理员 |
| 码点 | Unicode 码点。长度都按它数，一个四字节字符算一个 |

## 要求

每条三样：一句要求、来源、怎么验。验收只用四种测试：单元测试不碰数据库；集成测试用进程内数据库打真路由，凡要读库的断言都放这里；契约测试读生成的接口文档；端到端起真浏览器。

几样通用做法，下文不重复：

- 涉及仓库的验收把 `PROJECTS_ROOT` 指到临时目录，用真的 git；git 执行器可换成桩，同工程规格。
- 涉及代理进程的验收用仓里的假助手（A-27），或者把模块注入的进程启动器换成桩。
- 涉及等待的验收用注入的时钟拨表，不真等。
- 检查件（A-30）和可见性一样是构造参数，测试换成桩。

| `GET /api/v1/overview` | user | 无 | 200 `{ "projects": ProjectState[] }`，只含调用者看得见的工程 |
| `GET /api/v1/projects/{projectId}/sessions` | user | 无 | 200 `{ "sessions": Session[] }` |

| `GET /api/v1/projects/{projectId}/sessions/{sessionId}` | user | 无 | 200 `{ "session": Session }` |
| `POST /api/v1/projects/{projectId}/sessions/{sessionId}/start` | user | `{ "assistant"?: 助手编号, "reset"?: 布尔 }` | 200 `{ "session": Session }`，状态是 starting 或 running |
| `POST /api/v1/projects/{projectId}/sessions/{sessionId}/stop` | user | 无 | 200 `{ "session": Session }`，状态是 stopped |
| `POST /api/v1/projects/{projectId}/sessions/{sessionId}/interrupt` | user | 无 | 200 `{ "session": Session }` |
| `POST /api/v1/projects/{projectId}/sessions/{sessionId}/messages` | user | `{ "text": 正文, "attachments"?: 附件编号数组 }` | 201 `{ "entry": Entry, "session": Session, "inspection": Inspection }` |
| `GET /api/v1/projects/{projectId}/sessions/{sessionId}/transcript` | user | 查询串 `after`、`before`、`limit` | 200 `{ "entries": Entry[], "lastSeq": 数字, "hasMore": 布尔 }` |
| `POST /api/v1/projects/{projectId}/attachments` | user | multipart，恰好一个文件 | 201 `{ "attachment": Attachment }` |
| `POST /api/v1/projects/{projectId}/sandboxes` | user | `{ "task": 任务名, "assistant"?: 助手编号 }` | 201 `{ "sandbox": Sandbox }`；同名的在役沙盒已有时 200，回已有的 |
| `GET /api/v1/projects/{projectId}/sandboxes` | user | 无 | 200 `{ "sandboxes": Sandbox[], "quota": 数字 }` |
| `POST /api/v1/projects/{projectId}/sandboxes/{sandboxId}/merge` | user | 无 | 200 `{ "sandbox": Sandbox }`，状态是 merged |
| `POST /api/v1/projects/{projectId}/sandboxes/{sandboxId}/discard` | user | `{ "force"?: 布尔 }` | 200 `{ "ok": true }` |
| `POST /api/v1/receipts` | public，处理函数里验会话凭据 | 见 A-61 | 201 `{ "receipt": Receipt }` |
| `GET /api/v1/receipts` | user | 查询串 `after`、`audience`、`projectId` | 200 `{ "receipts": Receipt[], "nextAfter": 数字, "hasMore": 布尔 }` |

`Assistant` 一律是 `{ "id", "name", "available" }` 三个键。

`Session` 一律是十三个键：`{ "id", "projectId", "kind", "name", "assistant", "sandboxId", "status", "working", "createdById", "createdAt", "lastActivityAt", "lastSeq", "lastExit" }`。`kind` 是 main、chat、sandbox 三者之一。`name` 主会话是空串。`sandboxId` 只有沙盒会话有值，其余是空串。`status` 是 stopped、starting、running 三者之一。`working` 是布尔，只在 running 时有意义。`createdById` 是创建人的账号编号，不是人触发的（对账、以后队列建的）为空。`lastSeq` 是轨迹最后一条的序号，没有轨迹是 0。`lastExit` 是 `{ "at", "code", "reason" }` 或空；`reason` 是 person（人停的）、platform（平台自己收的：关停、合入后收回、废弃）、platform_restart（启动对账时发现它已经没了）、start_timeout（拉起后没就绪）、exited（进程自己退出的）五者之一。

`ProjectState` 是 `{ "projectId", "session", "activeSandboxes", "conflictSandboxes", "runningChats" }` 五个键；`session` 是这个工程的主会话，还没建出来的时候是空。

`Entry` 是九个键：`{ "seq", "kind", "text", "tool", "callId", "senderId", "attachments", "at", "truncated" }`。`kind` 是 user、assistant、thinking、tool_call、tool_result、system 六者之一。`tool`、`callId` 只在工具调用和工具结果上有值，其余是空串。`senderId` 只有人发的消息有值（账号编号），平台自己发的是空。`attachments` 是 `{ "id", "name", "size" }` 的数组，没有就是空数组。`truncated` 是布尔。

`Attachment` 是 `{ "id", "name", "size", "kind" }` 四个键；`kind` 是 image 或 file。

`Sandbox` 是十五个键：`{ "id", "projectId", "task", "branch", "sessionId", "state", "ahead", "behind", "dirty", "baseCommit", "mergeCommit", "createdById", "createdAt", "mergedAt", "lastConflictAt" }`。`state` 是 idle、dirty、ready、conflict、resolved、merged、missing、unknown、discarded 九者之一。`ahead` 是任务分支上有、默认分支上没有的提交数，`behind` 反过来。还没有的提交号和时间是空；算不出来的 `ahead`、`behind` 也是空。

`Inspection` 是 `{ "verdict", "hits" }` 两个键；`verdict` 是 passed 或 redacted（拦截时不回 201）；`hits` 是 `{ "type", "count" }` 的数组。`Receipt` 见 A-61。

编号都是 UUID；序号是整数；时间是带时区的 ISO 8601；「是不是」是布尔。路径里的 `projectId`、`sessionId`、`sandboxId` 都是编号，不是短名、任务名。

| 错误码 | 状态码 | 什么时候 |
|---|---|---|
| `sessions_name_taken` | 409 | 聊天位或沙盒的名字已被占用 |
| `sessions_quota_exceeded` | 409 | 聊天位或沙盒到了配额 |
| `sessions_assistant_unavailable` | 409 | 要用的助手此刻不能用 |
| `sessions_sandbox_busy` | 409 | 合入时代理正在处理 |
| `sessions_sandbox_nothing_to_merge` | 409 | 沙盒没有未合入的提交，或者已经合入、废弃 |
| `sessions_sandbox_closed` | 409 | 沙盒已经合入或废弃，不能启动它的会话 |
| `sessions_sandbox_conflict` | 409 | 合入撞上冲突，默认分支没动 |
| `sessions_sandbox_unmerged` | 409 | 废弃时要带强制：有未合入的提交，或者有未提交的改动 |
| `sessions_message_blocked` | 422 | 检查件判了拦截（发消息、交回执两条路） |

| `sessions_merge_failed` | 500 | 合入时 git 失败或超时，不是冲突 |

找不到和看不见一律是已有的 `not_found`（404）；形状不合是已有的 `invalid_request`（400）；没登录是 `auth_required`（401）。`message` 是给人看的，文案不固定。

### 会话的一生

| 编号 | 要求 | 来源 | 验收 |
|---|---|---|---|

**一、旧系统怎么跑一个会话**

- 一个会话就是一个 tmux 会话，里面跑助手的命令行界面。会话名是 `nexus-ai-<工程>`，任务会话是 `nexus-ai-<工程>--<任务>`（ai.py:89-90；deps.py:131-137）。启动是 `tmux new-session -d -x 220 -y 50 -c <目录> <命令>`（ai.py:226-227）；窗口开到 220×50，是因为界面只画一屏，屏小了没得滚（ai.py:224-225）。停止是结束 tmux 会话（ai.py:251-255）。
- 助手是一张写死的注册表，五家。其中一家的安装位置写死成某个用户家目录下的路径；启动旗标也写在注册表里，默认是跳过所有权限确认（ai.py:15、76-86）。其余几家每次用 `which` 找（ai.py:97-105）。模型和端点由服务器上另装的工具管，这里只管拉起（ai_routes.py:145）。
- 喂消息是逐行送键，睡 0.8 秒发回车，再睡 1.2 秒补发一个回车：界面会把紧跟文字的回车当成粘贴吞掉。斜杠命令例外，只发一个回车，否则第二个回车会替人确认选择器（ai.py:258-279）。两次睡都在请求里，一条消息至少占两秒。
- 读输出有两条路：老路截屏，取最后 40 行的末尾 2000 字（ai.py:282-292）；新路读助手自己落的轨迹文件（ai.py:322-338）。此外还有原样看终端画面的字节流（R016）和截屏差分推送（R020）。
- 「屏尾文本」就是截屏去掉首尾空白后的末尾 2000 字（ai.py:289-292）。「工作态」是猜的：轨迹最后一条的类别是人话、工具调用、工具结果或思考，并且文件 10 分钟内写过，就算在干活；斜杠命令的回显要特判（ai.py:295-319）。没有任何信号告诉平台，代理是开始干了还是干完了。
- 为了躲过平台重启时的连坐，会话启动后用 sudo 把 tmux 的进程树写进另一个 cgroup（ai.py:155-190、246）；写不成只落一行日志。台账记着一次发布重启还是把会话打死了（旧仓 `docs/BUGS.md` 第 165 行）。
- 启动前先往助手的家目录配置里写「这个目录已信任」，免掉要用方向键点的信任对话框；写不成就说还有按键通道兜底（ai.py:117-130、134-147）。还往助手的环境里注入一个第三方记忆层的令牌，令牌从共享盘上的一个文件读（ai.py:64-74）。
- 脆弱的地方，读码所见：按键时序靠睡；就绪靠睡 3 秒（sandbox_routes.py:151、183；queue.py:346、464）；会话和轨迹文件的对应靠盯新文件的线程，启动后盯 20 秒、缺映射再盯 60 秒（ai.py:672-748）；主会话的映射是启动时的快照，文件轮转后对话视图冻结在旧文件（ai.py:625-628 的注释）；解析结果有缓存，同一个文件 0.8 秒内再读直接回旧的（ai.py:418-438）；只有那一家的助手读得到轨迹，别的助手读对话直接报错（ai.py:547），页面退回看终端画面（dev.html:2627）。
- 新版由平台直接监管进程、拿结构化的输出之后，自然消失的：按键时序、就绪等待、信任对话框、窗口尺寸、截屏、轨迹文件和钉映射、工作态的猜测、按回环地址放行、cgroup 迁移。
- 新冒出来的：平台成了进程的监护人，泄漏的进程、关停的顺序、并发的上限都是它的账；输出翻译错一点就丢事件或者重复，所以每个适配器要有一致性测试（A-27）；每个会话一个进程，内存是账；代理打印的一切都进库，它读到的秘密也进（A-30、A-68）；凭据下放给了代理进程（A-25）；代理以服务用户运行，没有操作系统级的隔离（这一片接受，记待办 B-017）；就绪之前发来的消息要先排队（A-13）。

**二、对话轨迹从哪来**

- 读的是助手自己写的私有文件（ai.py:336-338）。每次把整份文件读进来解析，再按窗口选段（ai.py:423-438、523-559）。条目的序号是「这一遍解析出来的第几条」（ai.py:413-414）：文件换了、某一行解析失败了，序号就挪位。
- 条目五种：人说的话、助手的话、思考、工具调用、工具结果（ai.py:352-415）。工具结果截到 2000 字、思考截到 3000 字、工具参数截到 800 字，解析时就截，没有标记，全文无处可取（ai.py:398、407、411）。
- 增量是带着上次的最后序号来取之后的；向前翻页是带着最前面的序号取之前的若干条；按任务过滤是按会话键查映射册（ai.py:554-559；ai_routes.py:372-394）。页面 2 秒一拉，发完消息立刻补拉一轮，连续 3 次读不到就退回终端画面（ai-render.js:224、244-249、331）。
- 发送人是另记的。发送时往轨迹目录写一份旁账，记文本指纹（空白归一后前 300 字的散列）和时刻（ai.py:446-470）；读轨迹时按指纹回贴，对不上再按前后 5 秒就近贴（ai.py:481-520；`test_ai_msg_sender.py` 钉着）。旁账只读最后 4000 行，写失败静默（ai.py:457-469、473-478）。机器通道发的记成 local（ai_routes.py:241）。
- 页面有乐观气泡：发送成功先把原话画成虚线泡，等轨迹里出现同文的那条再转正；对不上不删（ai-render.js:268-291、341-351）。刷新之后泡没了是一个缺陷（旧仓 `docs/BUGS.md` 第 1812 到 1822 行），修法是把待转正的原话存进浏览器的 sessionStorage（dev.html:927-929、2848-2850）。
- 新版：平台写、落库、先落库再给页面看，发送人是条目上的字段（A-28、A-33、A-34）。

**三、完工回执**

- 契约写在四处，有三个版本。队列派单的任务书要求 `audience` 必须是 manager（queue.py:59-71）；工程入口文件的模板写的也是 manager（projects.py:144-151）；经理的职权书让经理验收报 manager、汇总报 platform（charter.py:62-70）；而下发规范的通知要求平台派的任务报 platform（`tools/dispatch_receipt_spec.py:10-17`）。经理这个角色 2026-11-12 退役了（deps.py:85-89），照前两处发的回执进了一条没有人读的通道。
- 入口只认直连对端是回环地址（ai_routes.py:424-429）；来源是请求体里自报的（ai_routes.py:433）。服务器上任何一个进程都能以任何工程的名义交回执，防伪造只有地址这一道。
- 结构化部分嵌在正文的一个代码块里，用正则抠出来再解析（receipt.py:28-62）；抠不出来或者不对，就标一个 unstructured，不报错，原文照存（ai_routes.py:450-453）。清点时看到：本机的镜像里，自 2026-11-06 起带解析结果的 145 条回执全部没有结构化（R023 的清点结论）。发回执的一方从来不知道自己发错了。
- 受众三种：user 是缺省，另有 platform 和 manager。后两种进事件中枢，user 不进（ai_routes.py:437-438、456-464；`test_cybercore_m2.py` 第 320 到 346 行钉着）。出站也过一遍规则层安检（ai_routes.py:444）。正文截到 4000 字（ai_routes.py:446）。
- 读的几处，读码所见：每次把整个文件读进来逐行解析（ai_routes.py:480-481），文件只追加、不轮转（ai_routes.py:454-455）；回最后 200 条，游标却按全部匹配的算（ai_routes.py:495），两次轮询之间新来的超过 200 条时，前面那些永远取不到；序号是毫秒时间戳（ai_routes.py:446），游标按小于等于跳过（ai_routes.py:484），同一毫秒的两条会被跳掉第二条；全通道读取曾对非管理员整面开放（旧仓 `docs/BUGS.md` 第 119 到 129 行）。
- 这一片做到入库和带游标的读（A-60 到 A-63）。留给第 8 片的：收件箱页面和已读位置（裁决清单里的 `receipt-read-state`）、分流到事件中枢之后的后果（落卡、挂起、派生事件）。

**四、沙盒的一生**

- 台账是一个工程一个文件，追加写，一行一个事件（建、合入、冲突、废弃、清残、派代理解冲突）；写失败静默（sandbox.py:62-87）。事件里的操作人一栏，路由侧从来不传，永远是空（sandbox.py:126；sandbox_routes.py:81；queue.py:449-450）。读台账只读最后 500 行（sandbox.py:205）：一个工程的台账攒过 500 行，更早的合入事件就看不到了，已合入会掉回别的状态。读码所见。
- 沙盒根在工程根目录下一个点前缀的目录里，一个任务一棵工作树（sandbox_routes.py:23-26）。分支是 `nexus-task/<工程>-<任务>`，基于开发分支，没有开发分支就用当前头（sandbox.py:28、40-41、146-147）。任务名只许字母、数字、短横线、下划线，40 个字符封顶（sandbox.py:30）。
- 清单是 git 的工作树清单并上台账（sandbox.py:188-220）；每个沙盒跑 4 次 git：脏树、领先数、落后数、头提交（sandbox.py:167-177）。状态七种：目录不在、空闲、有未提交改动、待合入、合入冲突、已解冲突、已合入。已合入只认台账的合入事件（sandbox.py:213-215）；已解冲突看落后数归零（sandbox.py:216-219）。`test_sandbox.py` 把建、幂等、合入链、脏树拒合、冲突中止、冲突两态、废弃强制闸、配额、清残都钉住了。
- 配额每个工程 2，写在每个工程自己的配置文件里（sandbox.py:33；sandbox_routes.py:33-37）。配的是工作树的个数，合完了不收也占着。队列两个任务合完就停摆，后来在队列里加了「配额满先回收已合入的工位」才绕开（queue.py:33-37、421-441）。自动回收靠任务名以字母 q 开头来认队列自己的沙盒（queue.py:430）：人在页面上建的名字恰好以 q 开头、零提交、工作树干净的沙盒，配额满时会被队列收走，而且那条路径不停它的会话。读码所见。`test_queue_sandbox.py` 第 244 到 262 行钉的只是「不以 q 开头的、脏的不碰」。
- 合入：要求开发工作树在开发分支上并且干净（sandbox.py:244-250）；`merge --no-ff` 恒产合并提交，文案是 `sandbox(<工程>): 合入任务沙盒 <任务>`；再显式推一次裸仓（sandbox.py:258-268；`test_sandbox.py` 第 60 到 82 行）。没有未合入的提交时记一笔空合入，回成功（sandbox.py:253-257）。推送失败只写进返回值和台账，路由照样回成功（sandbox.py:268-273；sandbox_routes.py:213）。手动合入不看沙盒的会话在不在干活（sandbox_routes.py:191-213）；队列那边等会话空闲才合（queue.py:295-298）。
- 冲突：整体撤回，开发分支不动，台账记一笔，状态是合入冲突（sandbox.py:260-266）。路由层接着给沙盒的会话发一条固定的解冲突指令，会话不在线就先拉起再派；派发的结果另记一笔台账；回 409，文案说明派没派成（sandbox_routes.py:162-210；`test_sandbox.py` 第 136 到 154 行）。沙盒的代理把开发分支并回自己的分支、落后数归零之后，人再点一次合入（`test_sandbox.py` 第 113 到 133 行）。队列那边最多派 5 轮、每 180 秒一轮，超了判失败、沙盒留场（queue.py:38-43、330-352）。
- 废弃：先停会话，再摘工作树、删分支；分支上有未合入的提交必须显式带强制（sandbox.py:277-303；`test_sandbox.py` 第 157 到 168 行）。两处漏洞，读码所见：工作树的目录已经不在时直接删分支，不查有没有未合入的提交（sandbox.py:282-289）；页面只在未合入提交数大于 0 时才带强制（dev.html:2467），零提交但有未提交改动的沙盒，git 拒绝摘除，在页面上废弃不掉。
- 清残是一个手动按钮：修剪工作树登记、删空目录（sandbox.py:306-321；dev.html:2521-2526）。
- 平台重启之后会话没了，队列的收尾是这样判的：会话不在、零提交，判失败；会话不在、但有提交，就直接合入（queue.py:314-319）。半截的活会被自动合进开发分支。读码所见。
- 聊天位和沙盒的差别：聊天位共享工程的开发工作树，没有分支、没有合入；沙盒有自己的工作树和任务分支，改完要合入。聊天位禁写靠助手的工具黑名单（sandbox_routes.py:137-143）；沙盒的代理带全套工具。聊天位的配额数的是活着的进程，默认 3（sandbox_routes.py:40-45、128-132）；沙盒的配额数的是工作树。聊天位和沙盒共用「工程--任务」这一个会话键的名字空间，重名回 409（sandbox_routes.py:124-127）。聊天位建成后睡 3 秒发一条契约首条（sandbox_routes.py:149-154）。没有删除聊天位的途径。

**五、主会话和态势**

- 一个工程一个主会话，会话名固定；已经在就续用，启动回 `started:false`（ai.py:1-3、202-204）。「可重置」是启动接口的一个参数：为真就先杀再起（ai.py:200-201）；两张页面从来不发真（dev.html:2380；devpage.html:1411-1420、1773-1791）。「可带任务名」也是启动接口的参数：带了就另开一个任务会话（ai_routes.py:29-34；deps.py:131-137）。
- 会话键对不上出过事：职能会话是单例，调用方带着任务后缀来，发消息恒 409，启动又回假成功（旧仓 `docs/BUGS.md` 第 1413 到 1422 行；`test_ai_task_of.py`）。
- 态势是每个工程一条：主会话在不在、在不在干活、最后一条的类别和序号，加任务清单，沙盒和聊天位各一行（在不在、在不在干活、状态、领先数、分支）（ai_routes.py:163-198）。每个工程探一次会话、读一次轨迹、列一次工作树，每个沙盒再来一遍；单个工程出错只丢那个工程（ai_routes.py:176-195）。
- 页面每 5 秒打一次汇总接口，一口气带回工程清单、服务器、态势、数据任务、待批数（tick_routes.py:22-39；dev.html:3927；devpage.html:2513）。打开几个人，服务器上就每 5 秒跑几轮子进程。

**六、发消息的路上发生了什么**

- 闸只有一道：看不看得见工程，挂在路由组上（ai_routes.py:23）。发消息另取一次身份，为了记发送人（ai_routes.py:226-227）。回环地址来的请求是全权管理员，发送人记成 local（auth.py:175-178；ai_routes.py:241）。
- 安检分两层。规则层：九类高置信的凭据模式，命中即脱敏成 `[REDACTED:类型]`，审计只记类型和次数，不落原文（security_scan.py:30-45、58-89、175-183）。灰区层：规则没命中、文本不超过 6000 字、又带触发词，才送本机的一个小模型去判；这是一次同步的外部调用，6 秒超时，模型不可达就放行（security_scan.py:110-134、137-155）。模型判「在向外传真实凭据」并且置信过 0.85 才拦，拦是抛异常，路由转成 422；0.55 到 0.85 之间放行，在响应里带回一个提示（security_scan.py:156-172）。`test_security_scan.py` 把九类脱敏、讨论不误杀、模型不可达放行都钉住了。
- 拦截时页面看到的是一句「安检拦截：消息疑似向外传输真实凭据」，消息没有发出去；页面把它当发送失败处理，原话还回输入框（ai_routes.py:237-238；dev.html:2852-2857）。脱敏时响应带回类型和次数，页面上加一行「已自动脱敏 N 项，AI 收到的是脱敏版」（dev.html:2832-2837）。
- 可是脱敏之后，页面上那一泡是原文：乐观气泡存的是发送前的原话，轨迹里回来的是脱敏后的，两者对不上，按「对不上不删」的规矩虚线泡一直留着，原话还写进了 sessionStorage（dev.html:2848-2850；ai-render.js:281、341-351；dev.html:927-929）。读码所见。
- 请求能带工作目录和启动参数（ai_routes.py:29-34、209-213；sandbox_routes.py:65-69、86）。看得见工程的人，都能让助手在服务器上的任意目录、带任意旗标启动。
- 事件中枢的规则命中之后，经回环地址直接打这个接口，把会话叫醒（engine.py:129-134）。所以它同时是机器通道。
- 回环放行能成立的前提：公网入口的请求经隧道和反向代理到达时，对端地址正是回环。旧系统靠反向代理带上真实地址，服务启动时按可信代理还原（旧仓 `server/deploy.sh` 第 70 行；反向代理对 `X-Forwarded-For` 是追加不是覆盖）。从转发头里取哪一个地址，由 Web 框架决定，而框架安装时不钉版本（同一个文件第 28 行）。现状有没有问题，没有实测。新版不按来源地址放行（A-25），这个问题就不在了。

**八、谁能做什么**

- 两张路由组只挂一道闸：看不看得见工程（ai_routes.py:23；sandbox_routes.py:19-20；deps.py:27-45）。看得见的人都能启动、停止、发消息、建沙盒、建聊天位、合入、废弃、清残。注释记着这道闸曾经整组缺失，任何开发者都能对别人的工程建沙盒、合入、废弃（sandbox_routes.py:19-20）。看不见回 403，文案说出工程名（deps.py:36-37）。
- 合入改的是工程的开发分支，并且推到裸仓，那是发布链的起点。谁能看见工程，由用户组定（人员规格 G-32）。
- 主会话是工程里所有人共用的，发送人旁账就是为了分清谁发的（ai.py:441-444）。停主会话、重置主会话，影响的是所有人。
- 服务器上的代理凭回环地址就是全权管理员：能停别人的会话、废弃别人工程的沙盒。身份规格记过，开发面的追加闸对回环请求直接放行（deps.py:52-53）。
- 新版：看得见就能做会话和沙盒的全部动作，合入也一样，编排者 2026-11-27 定；看不见一律 404（A-05）。凭据只够交回执（A-25）。

**九、活的状态怎么到页面上**

- 任务书对实时没有专门的条款；技术栈基线里列了「单向流和双向长连接各用其所」（任务书 §4.1）。
- 旧的全靠轮询：对话 2 秒（ai-render.js:224）、终端字节流 400 毫秒（dev.html:2600）、汇总 5 秒（dev.html:3927）、回执 60 秒（devpage.html:2514）。每次汇总在服务器上要跑的子进程见第五节。
- 对话在页面上流式出现，需要三样：平台先拿到结构化的输出事件（A-27）；每来一段就落库、让页面读得到（A-34、A-38）；页面不再靠乐观气泡去猜（A-71）。规格只定了时限。

**十、重启和失联**

- 平台进程重启：会话进程在 tmux 里，按设计不死，靠的是 cgroup 迁移；实际打死过（见第一节）。平台没有任何启动对账，谁在跑全靠每次去问 tmux；会话和轨迹的对应在一份映射册里，保存失败静默（ai.py:593-609），编号曾被并发写蹭掉（ai.py:740-742 的注释）。
- 服务器重启：tmux 会话全没了。再启动时按映射册里的编号续接同一篇对话（ai.py:216-222）。「长期保持」的意思是可恢复，不是进程常驻（ai.py:198-199）。
- 代理进程自己退出：没有专门的处理。状态只是不在了，页面一行「会话不在」（dev.html:2368、2595）；队列那边按「会话蒸发」处理（queue.py:314-318）。
- 页面知道的方式：汇总接口每 5 秒一次，状态变了要到下一拍才看得到。
- 新版：平台是进程的监护人，三种情形归结成两条（A-64、A-65），加上进程自己退出的如实记录（A-21）和没送达的说明（A-66）。

## 已裁决（2026-11-27）

规格代理带回八道题，编排者全部采纳它的推荐；正文就是按推荐写的。每条留一句裁决的理由，和它留下的尾巴。

1. **主会话和聊天位不能直接改代码（A-15）。** 说会话只拿到一份默认分支当时的检出，代理在里面改了什么平台一概不收；代码进默认分支只有沙盒合入这一条路。依据是共识文档 §十五 早已定下的「会话管说、任务管做」，而且队列从 0.54.62 起不再用主会话。尾巴：检出不随默认分支更新，这一片也不做自动刷新，要看新代码就重启会话。
2. **看得见工程的人就能合入（A-50、A-72）。** 和旧系统一样，不收窄到创建者和管理员。合入在机械上是安全的：冲突整体撤回，默认分支不动；页面上两步确认，事件记下操作人，合并提交可以整体回退。七个人的单位里，组员自己的活要等人点按钮是纯粹的等待。
3. **代理进程是平台的孩子（A-64、A-65）。** 平台关停就停，启动时把在跑的会话统一标成「平台重启时停的」，对话一条不少，发消息自动续上。代价是发布重启会打断正在跑的那一轮，轨迹里明说。换来的是不需要提权、没有孤儿进程、状态永远是真的。
4. **安检这一片只做规则层（A-30）。** 检查件可替换，这一片接上的是九类高置信的凭据模式，纯函数，不调外部服务。人会从第一天起往对话里贴配置，所以规则层要跟着这一片走；灰区模型那一层是最长 6 秒的同步外调，连同配置和管理面留给第 8 片。
5. **回执这一片只做数据面（A-60 到 A-63）。** 入库和带游标的读；凭据换成会话级的，结构化部分按形状校验，不再从正文里抠代码块。收件箱页面、已读位置、分流到控制芯核之后的后果留给第 8 片。
6. **合入成功就收回沙盒，清残不做成按钮（A-54、A-59）。** 工作树里还有未提交的改动时不收回，等人废弃。清残改成平台启动时自动对账。这两条都不是旧路由的原样。
7. **「打断本轮」做成正式的动作（A-18）。** 它不在这一片的旧路由清单里，是加的一条。旧页面靠给终端送一个键，这个形态随终端退役，需要留下来。
8. **这一片接受代理进程没有操作系统级的隔离（A-25、A-26）。** 代理以平台服务用户的身份跑，读得到别的工程的目录和平台自己的数据目录，旧系统一直如此。这一片只收紧三样：平台的环境变量不传给它，凭据只够交回执，不按来源地址放行任何请求。容器或系统级的隔离另立一片，记在待办 B-017。
