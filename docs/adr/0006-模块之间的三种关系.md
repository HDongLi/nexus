## 背景

第 3 片的规格代理带来一道题：「建工程时自动挂进创建者所属的用户组」该怎么接线。行为是定的——建完工程，同组的人立刻看得见，不用任何人再做一步（规格 P-12）。

两条现成的路各差一样。走事件：事件日志现在只写不投递，消费者是「事后」的，而验收要的是同一个请求返回时已经生效。同一个事务里调另一个模块、让它写自己的表：验收能过，但和铁律「模块之间不共享事务」的字面相冲。两个模块互相要对方的数据，直接 import 还成环。

根源不在接线，在归属：这份关系（哪个组看得见哪些工程）当时被放进了身份模块，于是工程模块建工程时必须回头找它。

## 决定

1. **模块之间只有三种合法的关系。** 调用对方出口（`index.ts`）公开的接口；订阅对方的事件；用自己的表对对方的表建引用约束。第三种是新明确的：引用的是对方出口导出的表定义，不是伸进对方的 `schema.ts`。
2. **引用约束不算读写对方的表。** 它只让库替两个模块把关，数据还是各写各的。铁律 7 的字面不用改。
3. **一份关系归「用它的模块」。** 一份关系要和某个模块自己的写入在同一个事务里同步生效，它就住在那个模块里，由那个模块在自己的事务里写。事件是「事后」通道：可以让别的模块事后做事，不能用来保证「现在就已经是这样」。
4. **完整性交给库。** 「建过工程的账号不许删」「挂进去的工程必须存在」这一类规矩，用引用约束保证（`ON DELETE RESTRICT` 或 `CASCADE`）。模块不先查后写：直接写，库拒绝了就把拒绝翻译成自己的失败码。应用层先查一遍，只是为了回得出看得懂的原因，不是保证。
5. **依赖只有一个方向，表和代码一致。** 表定义的引用方向就是模块的依赖方向；运行时的调用也只能顺着这个方向。反方向的调用没有，反方向的 import 也没有，所以不会成环。
6. **页面要两家的数据，由页面组合。** 后端不为了少一次请求而跨模块拼一个响应。

## 验证

- 依赖方向检查（`pnpm run arch`）核对没有任何文件伸进别的模块的内部文件。
- 集成测试绕过接口直接删一个建过工程的账号：库拒绝（SQLSTATE 23001）。这是决定 4 的直接证据，也是「先查后删之间有口子」这条顾虑的终结。
- 建工程的事务在写完关系之后抛错：工程记录、关系的行、两类事件都没有。这是决定 3 的直接证据。
- 两处独立审查（T-0020、T-0027）都对着这条裁决验收：架构闸的按模块表定义规则（T-0024）把它变成了机器闸。

## 后果

- 「哪个组看得见哪些工程」的关系表归工程模块，建工程时挂组是工程模块在自己的事务里写的；身份模块对工程一无所知。
- 用户组的响应里不带可见的工程，页面另问工程模块一条路由。多一次请求，换来两个模块互不相识。
- 删组时工程模块关系表里的行随约束删掉，没有工程模块的代码参与，也不发它的事件。事后要知道这个组当初看得见哪些工程，回放 `projects.visibility.changed`。
- 以后每加一份跨模块的关系，先问一句：它要和谁的写入同步？答案就是它的家。
