## 背景

任务书给写接口定的预算是 p95 不超过 200 毫秒。新建工程要建一个真的裸仓库：起四回 git（init、add、commit、clone --bare），时间基本花在起进程上。实测（开发机，8 核，进程内的库）：平静时中位数约 300 毫秒、p95 320–470 毫秒；机器被占满时 p95 到 640 毫秒。独立审查复测：中位数 310、p95 347。稳定超出预算。

## 决定

1. **接受例外：新建工程的预算记为 p95 ≤ 500 毫秒**，其它写接口仍是 200 毫秒。
2. **保持同步语义**：回 201 时仓库已可用（P-16），清单里立刻有它。不改成后台建仓加 202。
3. **重新裁的条件**：耗时超过 1 秒，或者建工程变成高频操作（比如以后做了「从模板批量建」），再考虑异步。

## 为什么

- 建工程是低频操作：一个单位就几个工程，一年加起来可能个位数。为它把接口语义复杂化（202 加轮询或推送、清单里的「建仓中」状态、失败时的对账），换来的是没人需要的几百毫秒。
- 「回 201 时仓库已可用」是四条路由里最简单可靠的一条不变式：调用方拿到成功就能 clone、就能推。异步会把它变成「成功但还不可用」，每个调用方都要多想一步。
- 四回 git 是内容正确的最小代价：要一个带初始提交的裸仓库，这几步省不掉；合并成一次 `fast-import` 能省进程数，但为低频操作增加一条不常跑的代码路径，同样不值。

## 后果

- 任务书 §10.3 在收口时补一句例外（「新建工程 p95 ≤ 500 毫秒」）。
- [模块卡](../../modules/projects/module.md)的「实测」一节记录了本机数字；换部署环境（服务器、真 Postgres）时量一遍新的，接近 1 秒就回到这张记录。
- git 的进程启动成本是主要项；换更快的盘或更轻的 git 参数能改善，但不改变结论。
